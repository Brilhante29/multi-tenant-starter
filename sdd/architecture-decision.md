# Architecture Decision

## Status

Accepted for implementation.

## Decision

Use a single-module hexagonal architecture with a PostgreSQL control plane in `public` and one physical schema per tenant.

```text
HTTP / benchmark
      |
application services
      |
small ports: registry | schema provisioning | tenant records | transaction | id
      |
Spring JDBC + PostgreSQL adapters
```

The application owns orchestration. Domain and use-case code have no Spring, JDBC, SQL, Docker, or transport imports. PostgreSQL adapters use fully qualified, validated schema identifiers and never trust a client-provided schema name.

## Transaction Boundary

`TenantService` executes registry insert, `CREATE SCHEMA`, tenant migration, and registry activation inside one `TransactionRunner.required` call. PostgreSQL transactional DDL makes failure rollback observable: no orphan schema and no partial registry state.

## Isolation Boundary

- Tenant IDs are generated by an output port; schema names derive only from UUIDs.
- `TenantContext` is established and cleared by `TenantDataService` in `finally`.
- The PostgreSQL record adapter resolves the active tenant from the registry and uses a validated, fully qualified schema.
- Each tenant table has a CHECK constraint binding `tenant_id` to its owning tenant.

## SOLID and Simplicity

- SRP: registry, schema lifecycle, scoped records, transactions, and IDs are separate responsibilities.
- OCP/LSP: adapters can change without use-case changes and test doubles obey the same ports.
- ISP: no broad datasource router exposes maps or database internals.
- DIP: services depend on ports, not Spring components.
- KISS/YAGNI: one database, JDBC, no ORM, broker, distributed transaction, or cloud service.
- DRY: one versioned tenant SQL migration is applied to every schema.

## Rejected Alternatives

| Alternative | Reason |
|---|---|
| In-memory schema map | Cannot prove PostgreSQL isolation, constraints, rollback, or concurrency. |
| Shared tables only | Changes the isolation model and weakens the project claim. |
| Hibernate multi-tenancy | Hides routing and DDL behavior behind ORM configuration. |
| Database per tenant | Stronger boundary but excessive startup and operational cost for this benchmark. |
| Modular monolith | Adds module ceremony without another bounded context. |

## Test Strategy

- Pure unit tests for use-case orchestration, validation, and context cleanup.
- Docker Compose integration tests for physical isolation, constraint enforcement, DDL rollback, and concurrency.
- Docker Compose benchmark against a clean PostgreSQL volume.
